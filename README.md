# Budget Manager

A private, single-user Android budgeting app. Reads bank SMS to detect spends, lets you review and accept or reject each one, tracks a budget per category per month (overspending shown as a negative number), and charts trends over time. All data stays on the phone.

- **Platform:** native Android, Kotlin + Jetpack Compose, MVVM, Hilt, Room, DataStore
- **Status:** M0 to M6 done (project foundation, domain core and database, SMS receive/catch-up, Messages page, Add Transaction and the accept flow, Monthly budget). There is no separate Categories page - category management (create, rename, reorder) lives on Monthly budget, and archiving was dropped from v1. M7 (Home and Category detail) built, not yet tested on-device. Every accepted credit counts for now (no way yet to tell real income apart from a friend settling up or a refund - revisit once that typed system exists). No schema change. A fifteenth, 2026-10-07: **the inclusion gate no longer requires an amount** - found by investigating a real report (5 September mutual fund investments, only 3 showed up), traced to `SpendClassifier`/`CreditClassifier` both requiring an amount pattern that some genuine transaction SMS (a SIP purchase confirmation pointing only to a separate statement) never state inline, silently dropping the message with no trace anywhere in the app. Amount requirement removed from both classifiers; the keyword requirement stays exactly as strict. Also fixed a related asymmetry found in the same pass: the credit side had no `will be credited` future-tense guard, unlike the debit side's existing `will be debited` one. The Messages row now shows "Amount unknown" instead of nothing for a message with no parsed amount, falling back to the linked transaction's real saved amount once Accepted. No schema change. A sixteenth, 2026-10-09: **a statement validator (CSV path)** - pick a bank/card CSV statement from Settings' new Data section, and see it compared against what SMS detection actually caught: coverage %, a statement-vs-in-app spend cross-check, and five grouped buckets (Needs review, Missing from our data - the one with an Add button, pre-filling Add Transaction - Rejected but on statement, Amount differs, and In our data but not on statement). A validator, not a second way to add transactions - nothing is ever saved automatically, and nothing from the comparison is kept once you close the page. A seventeenth, 2026-10-12: the validator now also reads **PDF (including password-protected PDFs) and Excel (.xls and .xlsx)**, not just CSV - `pdfbox-android` for PDF text extraction and password handling, Apache POI for legacy binary `.xls`, and a small hand-rolled zip+XML reader for `.xlsx` (avoiding `poi-ooxml`'s Android-unfriendly dependency chain). On-device testing surfaced a real bug no unit test had caught - the reverse swipe (Reminded → Pending) silently did nothing after a forward swipe had already fired, confirmed via direct database reads across 3 reproduction attempts. Root cause: `SwipeRow`'s `confirmValueChange` is captured once at a row's first composition and never updates - fixed with `rememberUpdatedState`, confirmed with a 4-swipe on-device round trip afterward. Since `MessageRow` shares this same component, this is almost certainly the same root cause as the still-open "swiping a Rejected message doesn't revert" report - not independently re-confirmed on Messages yet.
